# 자체 리뷰와 보고

5단계와 6단계에서 읽습니다.

## 자체 리뷰

내가 쓴 코드를 내가 리뷰하면 같은 맹점을 놓칩니다. 그래서 내 결론을 모르는 독립 서브 에이전트에게 리뷰를 맡깁니다.

### 한 회차

1. 리뷰를 맡깁니다. pstack의 `interrogate` 스킬을 쓸 수 있으면 그것으로 교차 검증합니다. 쓸 수 없으면 내장 `code-review` 스킬을 `high`로 실행합니다. 둘 다 쓸 수 없으면 `Agent` 도구로 서브 에이전트 두 개를 띄우고, 하나는 정확성, 다른 하나는 프로젝트 규칙 위반을 봅니다.
2. 리뷰어에게는 아래만 줍니다. 내 판단이나 "잘 된 것 같다"는 말은 주지 않습니다.
   - 티켓 ID와 완료 조건
   - `git diff origin/develop...` 와 커밋하지 않은 변경
   - 확정 케이스 목록
   - 읽어야 할 규칙 문서: 루트 `CLAUDE.md`, `_docs/wiki/dev-rules.md`
3. 지적마다 직접 코드를 보고 판정합니다. 리뷰어의 말을 그대로 옮기지 않습니다.
   - **고침**: 실제로 틀렸거나, 규칙을 어겼거나, 완료 조건을 못 채운다
   - **안 고침**: 취향 차이이거나, 티켓 범위 밖이거나, 근거가 추측뿐이다. 이유를 한 줄 남깁니다
4. 고친 뒤 확정 케이스의 테스트, 관련 단위 테스트, `npm run check`를 다시 실행합니다. 테스트 파일은 고치지 않습니다.

### 반복과 종료

- 고친 것이 있으면 새 서브 에이전트로 다음 회차를 돕니다. 이전 리뷰어를 다시 쓰지 않습니다.
- 한 회차에서 **고침** 판정이 하나도 없으면 끝냅니다.
- 3회차까지 돌았는데도 고침이 나오면 멈추고, 남은 지적을 보고에 적습니다. 같은 지적이 회차마다 되풀이되면 설계 판단이 필요한 문제이므로 고치지 않고 보고합니다.

## 보고

사용자가 커밋 전에 기능이 정말 끝났는지 직접 판단하기 위한 보고입니다. 길게 쓰지 않습니다. 사용자가 읽고 바로 브라우저를 열 수 있어야 합니다.

```markdown
## 4-75 구현 끝, 직접 확인 부탁드려요

목표: 티켓 목표를 한 문장으로

### 완료 조건
| 완료 조건 | 근거 |
| --- | --- |
| 1. ... | TC-90, TC-91 통과 |
| 2. ... | 직접 확인 필요 |

### 핵심 변경
- 3~5개. 무엇이 어디서 바뀌었는지
- 설계상 고민한 선택이 있으면 하나만

### 실행한 검사
- `npm run check` 통과
- 단위 N건, 통합 N건, E2E N건 통과
- 실행하지 않은 검사와 이유

### 직접 확인하는 방법
1. `npm run dev`
2. http://localhost:3000/... 접속
3. 무엇을 누르고 무엇을 입력
4. 기대하는 화면

### 남은 것
- 자체 리뷰에서 고치지 않은 지적과 이유
- 배포할 때 필요한 작업. 환경 변수 키, 마이그레이션
```

### 직접 확인 방법 쓰는 법

- `app/` 아래 라우트를 보고 실제 URL을 씁니다. 동적 경로는 실제로 쓸 수 있는 값을 찾아 넣습니다. 예: `units.ts`에 있는 단원 ID
- 로그인이 필요하면 Google 로그인을 먼저 하라고 씁니다.
- 스키마를 바꿨으면 로컬 개발 DB에 마이그레이션을 적용하는 명령을 앞에 씁니다.
- 화면에 보이지 않는 결과, 예를 들어 DB에 남은 기록은 `npm run db:studio`에서 어느 테이블의 어느 컬럼을 보면 되는지 씁니다.
- 실패 경우를 직접 확인하기 어려우면 "TC-번호가 확인"이라고 쓰고 단계에서 뺍니다.
