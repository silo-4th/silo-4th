# 테스트 케이스 작성 기준

2단계와 3단계에서 읽습니다. 케이스는 노션 Test-case DB가 원본이고 저장소에 파일로 만들지 않습니다. 근거는 `_docs/wiki/adr/0006-test-strategy.md`에 있습니다.

## 노션 DB

- DB: https://app.notion.com/p/40ce7e8fdd1280268097ef263f610f7a
- 데이터 소스: `collection://40ce7e8f-dd12-803f-96d6-000bb3af2de7`

속성 이름과 선택지가 바뀌었을 수 있으므로, 쓰기 전에 `notion-fetch`로 데이터 소스를 한 번 읽고 아래 표와 다르면 노션을 따릅니다.

| 속성 | 넣는 값 |
| --- | --- |
| 이름 | 테스트 이름에 들어갈 문장. `~해요`로 끝냅니다. 예: `단원 본문을 절로 나누고 절마다 겹치지 않는 주소 키를 붙여요` |
| 케이스 ID | 노션이 `TC-숫자`로 자동으로 매깁니다. 쓰지 않습니다 |
| 상태 | 새 케이스는 `초안`. AI는 `확정`으로 바꾸지 않습니다 |
| 테스트 유형 | `단위`, `통합`, `E2E` 중 하나 |
| 우선순위 | `높음`, `보통`, `낮음` |
| 위험 분류 | `데이터`, `권한`, `공통 변환` 중 해당하는 것. 없으면 비웁니다 |
| 핵심 기능 | `로그인`, `학습`, `확인`, `기록 조회` 중 해당하는 것 |
| Linear 이슈 | `[4-75](이슈 URL)` 형식. 여러 개는 쉼표로 잇습니다 |
| 확정일 | 비웁니다. 사람이 확정한 뒤에 채웁니다 |

본문은 DB 기본 템플릿과 같은 제목을 씁니다.

```markdown
## Given

테스트 전 조건

## When

입력 또는 사용자 행동

## Then

나와야 하는 결과

## Steps

E2E 케이스만 단계별로 적는다
```

## 조회

`notion-query-data-sources`의 SQL 모드로 이 티켓이 연결된 케이스를 읽습니다.

```sql
SELECT url, "케이스 ID", "이름", "상태", "테스트 유형"
FROM "collection://40ce7e8f-dd12-803f-96d6-000bb3af2de7"
WHERE ',' || REPLACE("Linear 이슈", ' ', '') || ',' LIKE ?
ORDER BY "케이스 ID"
```

`params`에는 `%,4-75,%`를 넣습니다. SQL 결과에서는 링크가 `4-75`처럼 글자만 남고, 여러 개는 쉼표로 이어집니다. 앞뒤에 쉼표를 붙여 비교해야 `4-7`이 `4-75`에 걸리지 않습니다. 본문이 필요하면 `notion-fetch`로 페이지를 읽고, `검토 중` 케이스는 `include_discussions`로 댓글도 읽습니다.

테스트가 이미 있는지는 `grep -rn "TC-<번호> " lib app e2e`로 확인합니다.

## 무엇을 케이스로 만드나

AI는 케이스를 너무 많이, 너무 촘촘하게 만드는 경향이 있습니다. 케이스가 많으면 설계를 바꿀 때마다 테스트를 함께 고쳐야 해서 변경이 어려워집니다. 그래서 **이 티켓의 목표를 달성했는지 증명하는 데 꼭 필요한 케이스만** 만듭니다. 한 티켓에 10개 안팎이 보통입니다.

만드는 것:

- 티켓의 완료 조건마다 성공하는 대표 경우 하나
- 틀리면 기록이 잘못 남거나 빠지는 경우
- 틀리면 다른 학습자의 기록을 읽거나 고칠 수 있는 경우
- 티켓이 명시한 실패 처리. 예: AI 호출이 실패해도 답을 막지 않는다

만들지 않는 것:

- 구현 방식을 고정하는 케이스. 함수 이름, 호출 순서, 내부 상태를 확인하는 것
- 같은 규칙을 입력만 바꿔 반복하는 케이스. 경계값이 규칙의 핵심일 때만 하나의 케이스 안에 묶습니다
- 프레임워크나 라이브러리가 이미 보장하는 동작
- 타입 검사나 린트가 이미 막는 것
- 티켓 범위 밖의 기능

## 테스트 유형 고르기

ADR 0006을 따릅니다.

| 유형 | 고르는 경우 |
| --- | --- |
| 단위 | 입력과 출력만으로 확인되는 변환 로직. 화면 안의 로직도 함수로 빼서 여기서 확인합니다 |
| 통합 | DB를 변경하거나 학습자별로 조회를 제한하는 서버 코드. 실제 테스트 DB에 남은 결과와 학습자별 접근 제한을 확인합니다 |
| E2E | 주요 사용자 흐름과 `async` 서버 컴포넌트. 대표 입력 한두 개로 흐름이 끝까지 이어지는지만 봅니다 |

같은 사실을 여러 유형으로 중복 확인하지 않습니다. 가장 아래 층, 즉 단위에서 확인할 수 있으면 단위로 둡니다.

## 겹침과 충돌 검토

노션에 넣기 전에 다음을 확인합니다.

- 두 케이스가 같은 Then을 확인하면 하나로 합칩니다.
- 두 케이스의 Given이 같은데 Then이 서로 모순되면 티켓 해석이 엇갈린 것이므로 사용자에게 묻습니다.
- 다른 티켓에 이미 있는 확정 케이스와 겹치는지 `이름`으로 DB를 검색합니다. 겹치면 새로 만들지 않고 그 케이스를 알립니다.
- 모든 완료 조건이 적어도 하나의 케이스로 덮이는지 확인합니다. 덮이지 않는 조건은 이유와 함께 보고합니다. 예: 화면 문구라 직접 확인으로 충분하다
