# design-qa 하네스 개선안

디자인 시안과 개발 화면을 비교하는 design-qa 하네스를 실제 티켓에 써 본 기록을 바탕으로, 왜 오래 걸렸는지와 어떻게 바꿀지를 정리한 문서예요. 2026-11-12 `develop` 브랜치 `6e3ff75` 커밋 위의 하네스를 기준으로 했어요.

하네스는 아래 파일로 이루어져 있어요.

- 반복 절차는 `.claude/skills/design-qa/SKILL.md`, QA 서브에이전트 지침은 `.claude/agents/design-qa.md`예요.
- 캡처와 상태 관리 명령은 `scripts/design-qa/cli.mts`이고, `npm run design-qa -- <명령>`으로 실행해요.
- 끝내기 조건은 Stop 훅 `.claude/hooks/design-qa-gate.mjs`가 강제해요.

## 한눈에 보기

- 티켓 하나에 QA만 1시간에서 2시간 반이 걸렸어요. 라운드 한 번이 7분에서 15분인데, 매 라운드가 처음부터 다시 하는 전수 검사였기 때문이에요.
- 지적을 기계로 다시 확인할 수 있는 단언으로 남기고, 다시 확인은 LLM 없이 `verify` 명령이 하게 바꿔요. LLM 라운드는 보통 전수 검사와 마지막 확인 두 번으로 끝나요.
- 기본 용도는 티켓 점검보다 develop에 머지된 화면을 길게 감사하는 쪽에 가까워요. 화면 목록, 한 번에 캡처, 화면별 동시 비교, 일부만 다시 감사하는 기능을 차례로 더해요.
- 이번에는 1단계와 2단계를 반영했어요. 3단계와 4단계는 제안이에요.

## 사용 기록

5개 티켓의 Claude 세션 기록에서 라운드별 지적 건수, QA 서브에이전트가 쓴 시간, 검사 명령 횟수를 뽑았어요. 시간은 서브에이전트 완료 알림의 실행 시간을 더한 값이라 대략이에요.

| 티켓 | 라운드별 지적 건수 | QA 에이전트 시간 합계 | 세션 길이 | `npm run check` 횟수 |
| --- | --- | --- | --- | --- |
| 4-146 | 20, 6, 9, 2, 2, 0, 0, 0 | 약 160분 | 341분 | 27 |
| 4-150 | 8, 4, 5, 0 | 약 70분 | 215분 | 20 |
| 4-149 | 14, 2, 0 | 약 65분 | 239분 | 19 |
| 4-148 | 8, 3, 2, 0, 2, 0 | 약 65분 | 217분 | 40 |
| 4-143 | 5에서 시작해 6라운드에 0 | 약 55분 | 211분 | 27, E2E 32 |

## 오래 걸린 이유

### 매 라운드가 전수 검사예요

1라운드에 20건이던 지적이 5라운드에 2건만 남아도, 새 QA 에이전트는 시안 소스를 다시 읽고 라우트를 다시 맞추고 단계 파일을 다시 쓰고 모든 화면을 다시 캡처했어요. 남은 지적 수와 상관없이 라운드 비용이 거의 같았어요. 가장 큰 낭비가 여기서 나왔어요.

### 0건이 나와도 믿기 어려웠어요

4-148은 4라운드에서 0건이었는데 5라운드에서 새 지적이 2건 나왔어요. 4-146은 2라운드 6건 다음 3라운드에 9건으로 늘었어요. 에이전트가 매번 다른 곳을 보기 때문이에요. 볼 목록이 정해져 있지 않으니 0건 한 번을 기다리는 방식은 운에 기대게 돼요.

### Stop 훅이 쓸모없는 라운드를 더 돌게 했어요

4-146은 6라운드에서 0건이 나온 뒤 7, 8라운드를 더 돌았고 둘 다 0건이었어요. 훅이 0건 라운드 뒤에 바뀐 파일을 테스트 파일까지 모두 셌기 때문이에요.

### 라운드마다 검사와 테스트를 돌렸어요

스킬이 라운드마다 `npm run check`와 관련 E2E를 돌리게 했어요. 4-148은 check를 40번, 4-143은 E2E를 32번 돌렸어요.

### 화면을 하나씩 순서대로 봤어요

에이전트 하나가 모든 화면과 상태를 차례로 봤어요. 화면끼리는 서로 기대지 않는데도 동시에 보지 않았어요.

### 용도가 맞지 않았어요

티켓 하나를 점검하기에는 무겁고, develop 전체를 길게 감사하기에는 화면 목록, 이어서 하기, 화면별 분할, 이슈로 넘기는 출력이 없어요. Stop 훅이 티켓 작업 중 턴을 계속 막는 것도 방해가 됐어요.

## 개선 방향

핵심은 두 가지예요. 지적을 기계로 다시 확인할 수 있는 형태로 남기면 n라운드 반복이 필요 없어져요. 그리고 기본 용도를 develop 감사로 두고, 티켓 점검은 그 결과를 가져다 쓰는 가벼운 모드로 둬요.

| | 지금 | 개선 뒤 |
| --- | --- | --- |
| 주 용도 | 티켓 작업 중 n라운드 반복 | develop 감사, 티켓 점검은 보조 |
| 캡처 | 에이전트가 단계를 써서 화면마다 따로 | 스크립트가 전 화면을 한 번에 |
| 비교 | 에이전트 하나가 순서대로 | 화면 묶음별 에이전트가 동시에 |
| 다시 확인 | 매번 새 에이전트로 전수 검사 | `verify`가 단언만 비교 |
| 끝내는 기준 | 0건이 한 번 나올 때 | 단언이 모두 통과하고 마지막 확인 라운드에 새 지적이 없을 때 |
| Stop 훅 | 모든 변경을 셈 | 화면 코드 변경만 셈 |
| 검사와 테스트 | 라운드마다 | 보고 직전에 한 번 |

## 단계별 계획

### 1단계. 훅과 스킬의 낭비 줄이기

Stop 훅이 화면 코드 변경만 세게 하고, 스킬에서 라운드마다 검사와 테스트를 돌리는 단계를 빼요. 4-146의 7, 8라운드 같은 낭비와 반복 검사 시간이 바로 줄어요. 이번에 반영했어요.

### 2단계. 지적을 단언으로 남기고 `verify`로 다시 확인하기

값으로 비교할 수 있는 지적에는 `check`를 달아요. `verify` 명령은 개발 화면을 열어 단언만 다시 비교하고, LLM을 쓰지 않아요. 고치고 다시 확인하는 반복을 이 명령으로 돌리고, LLM 라운드는 전수 검사와 마지막 확인에만 써요. 이번에 반영했어요.

### 3단계. 화면 목록, 한 번에 캡처, 동시 비교

`scripts/design-qa/screens.json`에 시안 경로, 개발 경로, 상태별 진입 단계를 한 번 정리해 커밋해요. `capture` 명령이 목록의 모든 화면을 양쪽에서 캡처하고 스타일을 뽑아요. 감사에서는 `next dev` 대신 `next build`와 `next start`로 띄워 화면마다 컴파일을 기다리지 않게 해요. 화면 묶음마다 QA 에이전트를 동시에 띄워요. 제안이에요.

### 4단계. 일부만 다시 감사하고 보고서와 이슈 초안으로 내기

감사마다 시안 커밋과 develop 커밋을 기록하고, 다음 감사에서는 소스가 바뀐 화면만 다시 봐요. 결과는 화면별 지적과 캡처를 나란히 둔 보고서와, 컴포넌트 단위로 묶은 Linear 이슈 초안으로 내요. 이슈는 분리안을 먼저 보고하고 승인을 받은 뒤 만들어요. 제안이에요.

## 이번에 반영한 것

### 지적의 `check`

QA 에이전트는 값으로 확인할 수 있는 지적에 `check`를 달아요. `check`는 개발 쪽 단계 파일 `steps`, 실행 옵션 `args`, `selector`와 아래 셋 중 하나로 이루어져요.

| 모양 | 비교 방법 |
| --- | --- |
| `prop`, `expected` | 첫 번째로 맞는 요소의 계산된 스타일 값을 문자열로 비교해요 |
| `text` | 첫 번째로 맞는 요소의 글자를 연속 공백을 정리해 비교해요 |
| `count` | 셀렉터에 맞는 요소 수를 비교해요. 0이면 없어야 한다는 뜻이에요 |

`check`가 없는 지적은 배치나 이미지처럼 다음 QA 라운드가 눈으로 다시 봐야 하는 지적이에요. QA 에이전트는 결과를 쓴 뒤 `verify --round NN`으로 이번 `check`가 지금 모두 실패하는지 확인해요. 지금 통과하는 `check`는 잘못 쓴 것이기 때문이에요.

### `verify` 명령

`npm run design-qa -- verify`는 모든 라운드의 `check`를 개발 화면에서 다시 확인해요. LLM은 쓰지 않아요. 단계 파일과 옵션 조합마다 화면을 한 번만 열고, 실패한 지적을 id, 기대값, 실제값으로 한 줄씩 출력해요. 결과는 `.design-qa/verify.json`에 남아요.

로그인 화면 `check` 3개로 실제 개발 서버에서 확인했어요. 제목 띄어쓰기를 일부러 틀리게 바꾸면 그 지적만 실패했고, 되돌리면 3개 모두 통과했어요. 한 번 실행에 4.6초가 걸렸어요. 앞에서 측정한 LLM 라운드 한 번은 7분에서 15분이었어요.

### 반복 절차

1. 1라운드에서 전수 검사를 해요.
2. 고친 뒤에는 `verify`만 반복해요.
3. 2라운드는 마지막 확인이에요. 앞 라운드의 `check` 있는 지적은 다시 적지 않고, 새 차이와 `check` 없는 지적만 봐요.
4. `check` 없는 지적이 남을 때만 다음 라운드를 돌려요.

`npm run check`와 E2E는 라운드마다 돌리지 않고 끝내기 직전에 한 번만 돌려요.

### Stop 훅

판정을 함수 하나로 모았어요. 화면 코드는 `app/`, `lib/`, `public/` 아래에서 테스트 파일을 뺀 파일만 세요.

- 최신 라운드가 0건이면, 그 뒤로 화면 코드가 바뀌지 않았거나 바뀐 뒤 `verify`가 통과해야 끝낼 수 있어요.
- 최신 라운드에 지적이 있으면, 2라운드 이상이고 남은 지적이 모두 `check`가 있으며 `verify`가 통과해야 끝낼 수 있어요.

가짜 상태로 만든 24가지 경우와 실제 개발 서버 상태로 판정을 확인했어요.

### 남은 위험

- 0건 라운드 뒤에 화면을 바꿔도 `verify`만 통과하면 끝낼 수 있어요. 그래서 `check`가 없는 배치 회귀는 이 경우에 다시 보지 않아요.
- `--fresh-learner`나 `--unconsented`가 든 `check`는 `verify`를 돌릴 때마다 테스트 학습자를 새로 만들어요. `end`나 `cleanup`이 지우지만, 반복하는 동안에는 쌓여요.
- 화면 파일을 지우기만 한 변경은 화면 변경으로 세지 않아요. 지운 파일에는 수정 시각이 없기 때문이에요.
