# Sentry 오류 수집 현황과 개선이 필요한 점

## 한 줄 요약

우리 코드가 직접 잡지 않고 맨 위까지 빠져나간 오류와 서버가 직접 보낸 오류만 Sentry로 간다. 화면이 예상해서 문구를 보여 주는 실패는 Sentry에 남지 않는다. 지금은 환경을 구분하지 않고 오류를 분류하지도 않아서, 알림만 보고는 어떤 오류인지 알 수 없다.

## 1. 지금 Sentry로 가는 오류

| 구분 | 잡는 곳 | 예시 이슈 | 학습자 화면 |
| --- | --- | --- | --- |
| 서버 API에서 직접 보낸 오류 | `lib/*.ts`의 `captureException`, 로그인 쪽 `reportAuthError` | `4TH-SILO-K` section-views 저장 실패 58회, 환경 변수가 비어 있다는 오류 여러 건 | API가 5xx를 돌려주고 화면이 실패 안내를 보여 준다 |
| 서버 렌더링 중 난 오류 | `instrumentation.ts`의 `onRequestError`가 자동으로 잡는다 | `4TH-SILO-E` `/study/:unitId` Suspense 경계 오류 246회, `/start`의 `AUTH_SECRET` 오류 | 화면에 따라 다르다 |
| 브라우저에서 아무도 잡지 않은 오류 | `instrumentation-client.ts`의 `Sentry.init`이 자동으로 잡는다 | 성능 측정 `TypeError` | 버튼이 반응하지 않는 식으로 보이거나 아무것도 안 보인다 |
| React가 스스로 복구한 오류 | `Sentry.init`이 자동으로 잡는다 | `4TH-SILO-N` Hydration 불일치 | 대개 알아채지 못한다 |
| 화면을 그리다 난 오류 | `app/global-error.tsx`가 에러 화면을 보여 주면서 `captureException`을 부른다 | `design-qa render error` 시험 오류, 빌드 오류 화면 | "문제가 생겼어요" 전체 화면이 뜬다 |
| 성능 이슈 | `tracesSampleRate: 1.0`이라 모든 요청을 추적하고 Sentry가 느린 쿼리를 찾는다 | `4TH-SILO-A` 연속 쿼리 2,019회, Slow DB Query, N+1 Query | 영향이 보이지 않는다 |

앱에는 `error.tsx`가 없어서 화면 렌더링 오류는 모두 `global-error.tsx`까지 올라간다.

## 2. 지금 Sentry로 가지 않는 오류

| 구분 | 지금 처리 | 예시 |
| --- | --- | --- |
| API가 일부러 돌려준 4xx | 라우트가 본문 없이 상태 코드만 돌려주고, 화면이 `response.ok`를 보고 안내를 보여 준다 | 로그인 안 됨 401, 없는 단원 404 |
| 화면이 받은 5xx | 화면은 실패 안내만 보여 준다. 서버가 이미 보낸 경우에만 기록이 남는다 | 퀴즈 생성 실패 502 |
| `try`, `catch`로 삼킨 오류 | 학습을 막지 않으려고 조용히 넘어간다 | `unit-body.tsx`의 학습 기록 전송 실패 |

## 3. 화면의 오류 처리 방식

| 항목 | 지금 상태 |
| --- | --- |
| 공통 오류 코드 | 없다 |
| API 실패 응답 | 대부분 `new Response(null, { status })`로 본문 없이 상태 코드만 돌려준다. 서버 안의 실패 종류, 예를 들어 `generation-failed`는 상태 코드로 바뀌면서 사라진다 |
| 화면 문구 | 질문 패널만 `failed`, `cut`, `signed-out`, `pending`을 나눠 `FAIL_MESSAGES`로 보여 준다. 나머지 화면은 `fail-state.tsx`의 "잠시 뒤 다시 시도해 주세요" 하나를 쓴다 |

## 4. 개선이 필요한 점

| 문제 | 영향 | 개선 방향 | 담당 |
| --- | --- | --- | --- |
| `environment`를 정하지 않는다 | 로컬과 preview 오류도 운영 오류와 섞여 알림이 온다. 환경 변수가 비어 있다는 오류는 로컬에서 났을 가능성이 크다 (추정) | `VERCEL_ENV`로 환경을 정하고 로컬에서는 보내지 않는다 | 4-62 하위 이슈 A |
| 오류를 분류하지 않는다 | 알림에 `Error`나 `종류 없음`만 보인다 | 오류 코드 카탈로그를 만들고 `beforeSend`에서 태그와 fingerprint로 붙인다 | 4-62 하위 이슈 A |
| 예상된 오류와 장애를 구분하지 않는다 | 로그인 취소, 만료된 세션 같은 오류도 건별로 알림이 온다 | warning으로 기록하고 급증할 때만 알린다 | 4-62 하위 이슈 A, B |
| 성능 이슈도 알림 대상이다 | 발생 횟수가 가장 많은 성능 이슈가 알림을 채운다 | 알림 조회를 `issue.category:error`로 제한한다 | 4-62 하위 이슈 B |
| 알림 제목이 이슈 코드다 | PO가 `4TH-SILO-C`만 보고는 무슨 오류인지 모른다 | 오류 코드의 한국어 요약을 제목으로 쓴다 | 4-62 하위 이슈 B |
| API 실패 응답에 오류 코드가 없다 | 화면이 실패 이유를 구분할 수 없어 같은 안내만 보여 준다 | 실패 응답 본문에 카탈로그와 같은 오류 코드를 싣고 화면이 코드별 문구를 보여 준다 | 제안. 4-62와 따로 진행한다 |
| 삼킨 오류가 기록되지 않는다 | 학습 기록 전송이 계속 실패해도 알 수 없다 | warning으로 기록할지 정한다 | 확인 필요 |
| 성능 이슈 자체 | 연속 쿼리와 N+1 쿼리가 반복된다 | 알림과 별개로 쿼리 개선을 검토한다 | 확인 필요 |

## 5. 논의에서 정한 것

| 항목 | 내용 | 정한 사람 |
| --- | --- | --- |
| 알림 개선과 화면 오류 처리의 관계 | 오류 코드 목록만 함께 쓰고 작업은 나눈다. 알림 개선이 화면 문구 결정을 기다리지 않게 하기 위해서다 | 제안. 개발자 승인 전이다 |
| 오류 코드 이름 | Sentry만 보고 짓지 않고 서버의 실패 종류로 짓는다. 예: `QUIZ_GENERATION_FAILED`, `SESSION_EXPIRED`. 나중에 API 응답에 같은 코드를 실을 수 있다 | 제안. 개발자 승인 전이다 |
