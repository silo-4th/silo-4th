# 0013. 이벤트 로그는 앰플리튜드 브라우저 SDK로 보내고, 자동 수집을 끄고 학습자가 쓴 글은 보내지 않는다

- 상태: 확정
- 결정 날짜: 2026-11-12
- 결정한 사람: 개발자
- 관련 문서: [이벤트 로그 설계 (스프린트 1)](https://linear.app/silo0/document/이벤트-로그-설계-스프린트-1-69fabb9afd12), [4-155](https://linear.app/silo0/issue/4-155), [0005](0005-sentry-error-monitoring.md), [개발 규칙](../dev-rules.md)

## 상황

꺼내 먹기, 퀴즈 탭, 첫 진입에서 학습자가 어느 단계에서 빠지는지 매일 봐야 했다. 가설 숫자는 DB로 계산하지만 화면 노출, 버튼, 기다린 시간은 DB에 남지 않는다. 이벤트 도구를 앰플리튜드로 쓰는 것은 팀 회의에서 정했다. 근거는 `output/2026-11-05-quiz-schema.md`의 "회의록 7번 이벤트 로그는 앰플리튜드로"와 설계 문서의 "한 문장 요약"이다.

설계 문서는 이벤트 이름, 속성, 보내는 시점과 함께 원칙 다섯 가지를 정했다. DB에 남는 값은 보내지 않고, 학습자가 쓴 글은 보내지 않고, 자동 수집은 끈다. 개발자는 이 원칙을 코드에서 어떻게 지킬지 정해야 했다.

2026-11-12 연동 때 확인한 내용은 다음과 같다. 근거는 `node_modules/@amplitude/analytics-core/lib/esm/types/config/browser-config.d.ts`다.

- `@amplitude/analytics-browser` v2는 `autocapture`를 끄지 않으면 페이지 조회, 클릭, 폼, 파일 다운로드, 유입 경로를 자동으로 보낸다.
- 원격 설정 `remoteConfig.fetchRemoteConfig`의 기본값이 켜져 있다. 켜 두면 앰플리튜드 화면에서 자동 수집을 다시 켤 수 있다.
- `init` 전에 부른 `add`, `setUserId`, `track`은 큐에 쌓였다가 `init` 뒤에 부른 순서대로 처리된다. 로그인 전 이벤트는 기기 ID로 묶이고, `setUserId`를 부르면 같은 학습자로 이어진다.

## 결정

브라우저 이벤트는 `@amplitude/analytics-browser`로 보내고, 초기화와 전송은 `lib/amplitude.ts` 한 곳에서만 한다. 이벤트 이름과 속성 타입은 `lib/analytics.ts`의 `AnalyticsEvents`에 둔다.

연동할 때 다음을 지킨다.

- `autocapture: false`와 `remoteConfig.fetchRemoteConfig: false`로 자동 수집과 원격 설정을 끈다. 진단 데이터 전송도 끈다.
- 이벤트 속성은 ID, 개수, 정해진 값만 둔다. 질문 원문, 답, 이메일, 이름이 들어갈 자리를 `AnalyticsEvents` 타입에 두지 않는다. 필요하면 글자 수처럼 숫자로 바꿔 보낸다.
- `landing_view`의 `referrer`는 전체 주소 대신 사이트 이름만 보낸다. 주소의 검색어에 개인정보가 섞일 수 있다.
- 모든 이벤트에 `app_version`과 `study_day`를 붙인다. 브라우저는 enrichment 플러그인이 붙이고, 서버는 보낼 때 붙인다.
- 로그인한 화면은 `IdentifyLearner`로 학습자 ID와 사용자 속성을 넣는다. 로그아웃하면 `reset`으로 학습자와 기기 ID를 새로 시작한다. 한 브라우저를 다른 학습자가 이어 쓸 수 있기 때문이다.
- 키는 `NEXT_PUBLIC_AMPLITUDE_API_KEY`로 읽는다. 브라우저에 실리는 프로젝트 식별값이라 비밀값으로 다루지 않는다. 키가 비어 있으면 아무것도 보내지 않는다.

서버에서만 알 수 있는 순간의 이벤트는 `lib/amplitude-server.ts`의 `trackFromServer`로 앰플리튜드 HTTP API에 보낸다. 지금은 `start_submit` 하나다. 시작 화면 저장은 학습 화면으로 보내는 redirect로 끝나서 브라우저가 저장된 순간을 알 수 없고, 이 redirect는 노션 TC-25가 확인하는 동작이다. 서버 이벤트는 `after()`로 응답 뒤에 보내 응답을 늦추지 않고, 실패해도 학습 흐름에 영향을 주지 않는다. 기기 ID 없이 학습자 ID로만 보내며, 브라우저가 로그인 때 같은 학습자 ID를 넣어 두어 이어진다.

설계 문서와 다르게 정한 것은 다음과 같다. 두 가지 모두 Linear에 댓글로 남겼다.

- 퀴즈 탭 `trigger`에서 `unit_change`를 뺐다. 단원을 바꾸는 것만으로는 문제를 생성하지 않아서, 단원을 바꾼 뒤의 요청도 `next`로 보낸다.
- `recall_study_click`은 심지 않았다. 결과 화면에 틀린 문제의 관련 개념으로 가는 버튼이 없기 때문이다. 버튼을 추가한 뒤에 심고, 그때까지 `recall_finish_click`의 `study_click_count`는 0으로 보낸다.

## 검토한 대안

| 대안 | 장점 | 단점 | 택하지 않은 이유 |
| --- | --- | --- | --- |
| 자동 수집을 켜 둔다 | 코드 없이 페이지와 클릭이 쌓인다 | 이름이 정해지지 않은 이벤트가 섞이고, 입력 요소의 글이 담길 수 있다 | 설계 문서 원칙 5와 맞지 않는다 |
| 이벤트 속성 금지어를 런타임에 걸러 낸다 | 실수로 넣은 값도 막는다 | 무엇이 글인지 이름만으로 가려낼 수 없다 | 타입에 자리를 두지 않는 쪽이 컴파일 단계에서 막는다 |
| `start_submit`을 브라우저에서 보낸다 | 서버 코드가 늘지 않는다 | 저장 성공을 알려면 서버 액션이 redirect 대신 결과를 돌려줘야 한다 | TC-25가 redirect를 확인한다 |
| `start_submit`을 제출 버튼을 누를 때 보낸다 | 구현이 단순하다 | 저장이 실패해도 보낸다 | 설계 문서는 저장됐을 때 보내라고 정했다 |
| SDK를 화면이 뜬 뒤에 따로 받는다 | 첫 화면 스크립트가 압축해서 약 68KB 줄어든다 | 받기 전 이벤트를 모아 두는 코드가 필요하다 | 지금은 그대로 두고 성능을 측정한 뒤 개선한다. 개발자가 2026-11-12에 정했다 |

## 결과

- 정해진 이름의 이벤트만 쌓여 차트를 바로 만들 수 있다.
- 이벤트에 학습자가 쓴 글을 넣으려면 `AnalyticsEvents` 타입부터 고쳐야 해서 코드 리뷰에서 드러난다.
- 로그인 화면이 처음 받는 스크립트가 압축해서 약 68KB 늘었다. 2026-11-12 운영 빌드로 측정했을 때 전체 289KB의 약 24%다.
- 광고 차단 확장 프로그램이 앰플리튜드 요청을 막으면 이벤트가 빠진다. 가설 숫자는 DB로 계산한다.
- 키는 Vercel Production 환경에만 넣었다. Preview 배포와 키가 없는 로컬에서는 이벤트를 보내지 않는다.
- 개발 모드에서는 React StrictMode 때문에 화면 노출 이벤트가 두 번씩 간다. 운영 빌드에서는 한 번만 간다.

## 다시 검토할 조건

- 첫 화면 성능이 문제가 되면 SDK를 화면이 뜬 뒤에 받도록 바꾼다.
- 결과 화면에 관련 개념으로 가는 버튼이 생기면 `recall_study_click`을 심고 `recall_items.opened_section_at`을 채운다.
- 단원을 바꾸면 바로 문제를 만드는 흐름이 생기면 `unit_change` 트리거를 다시 넣는다.
