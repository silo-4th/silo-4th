# 0014. 브라우저가 받는 서버 데이터는 TanStack Query로 관리하고, 컴포넌트 사이에서 나누는 상태만 Zustand로 옮긴다

- 상태: 확정
- 결정 날짜: 2026-11-18
- 결정한 사람: 개발자
- 관련 문서: [0006](0006-test-strategy.md), [0013](0013-amplitude-event-logging.md), [개발 규칙](../dev-rules.md)

## 상황

학습 화면의 상태는 클라이언트 컴포넌트 24개, 약 3,900줄에 있다. 상태가 몰린 곳은 `app/study/(unit)/_components/question-panel.tsx`, `study-panel.tsx`, `recall-gate.tsx`와 `lib/quiz-tab.ts`다. 단원 본문과 학습자는 서버 컴포넌트가 받으므로 이 결정의 범위가 아니다. 범위는 브라우저가 `fetch`로 받아 `useState`에 넣는 서버 데이터와, 여러 컴포넌트가 함께 읽는 클라이언트 상태다. 아래 내용은 2026-11-18 `develop` 브랜치 코드로 확인했다.

서버 데이터에서 확인한 문제는 다음과 같다.

- 받는 함수가 화면마다 따로 있다. `fetchJson`이 `question-panel.tsx:82`와 `lib/quiz-tab.ts:204`에 두 벌 있고, 실패를 각각 `undefined`와 `Fetched<T>`로 돌려준다. `lib/past-problems.ts`, `lib/quiz-card.ts`도 `fetch`와 `try/catch`를 따로 쓴다.
- 로딩, 실패, 다시 시도를 컴포넌트마다 손으로 만든다. `"loading" | "failed" | "done"` 상태, 다시 시도용 숫자, 늦게 온 응답을 버리는 `active` 플래그가 대화 목록 `question-panel.tsx:131-132, 192-205`, 지난 문제 `past-problems.tsx:25-41`, 퀴즈 홈 `study-panel.tsx:436-445`에 반복된다.
- 캐시를 직접 만든다. 이미 받은 대화는 `loadedSessions` ref와 `sessionLoads` 상태로 기억하고 `question-panel.tsx:128-162`, 질문을 보내면 대화 목록 순서를 `setSessions`로 직접 바꾼다 `question-panel.tsx:286`.
- 캐시와 무효화가 없어 같은 데이터를 다시 받는다. 퀴즈 홈은 퀴즈 탭을 열 때마다 새로 마운트되어 `/api/quiz-home`을 다시 부르고 스켈레톤을 띄운다 `study-panel.tsx:340, 349`. 지난 문제도 열 때마다 `/api/quiz-attempts`를 다시 부른다 `past-problems.tsx:23`. 둘 다 최신 값을 보여 주려고 일부러 택한 방식이라 화면이 틀린 값을 보여 주지는 않는다.

퀴즈 홈 값에는 무효화를 단순하게 만드는 성질이 있다. `hasUnitCandidates`는 그 단원에서 본 절이나 질문한 절이 하나라도 있으면 참이다 `lib/quiz-problems.ts:122-133`. 한 번 참이 되면 다시 거짓이 되지 않는다. 질문의 개념 분류는 답을 만들기 전에 끝난다 `lib/questions.ts:270-273`.

클라이언트 상태는 흐름 규칙을 순수 함수 `advanceQuizSet`, `advanceRecall`, `startQuizFlow`에 두고 단위 테스트하고 있어 구조가 대체로 좋다. 확인한 문제는 다음과 같다.

- `useQuizSet`은 비동기 응답에서 지금 상태를 읽으려고 상태를 ref에 한 번 더 복사한다 `study-panel.tsx:95-112`. `openUnit` ref도 같은 이유로 있다. 두 값을 맞추는 일은 사람이 맡는다.
- 본문과 학습 패널을 잇는 `selection-ask.tsx`의 `createChannel`은 리스너 Set, `ready` 값, 구독 함수를 직접 구현한 작은 외부 스토어다.
- 브라우저 저장소를 읽고 쓰는 코드가 말투 `lib/answer-tone.ts`, 풀던 문제와 묶음 완료 `lib/quiz-tab.ts:246-308`, 열린 대화 `question-panel.tsx:68-80`에 세 벌 있다.
- `QuestionPanel`에 `useState`가 13개 있고, 서버 데이터와 받는 중인 답변, 메뉴 같은 UI 상태가 섞여 있다.

## 결정

1단계는 [4-158](https://linear.app/silo0/issue/4-158)에서 적용했다. 2단계는 로딩이나 요청 수와 관계없어 따로 이슈를 만든다.

1단계로 TanStack Query `@tanstack/react-query`를 들여 다음 서버 데이터를 옮긴다.

| 데이터 | 쿼리 키 | 무효화 시점 |
| --- | --- | --- |
| 대화 목록 `/api/question-sessions` | `["sessions"]` | 질문을 보낼 때 `setQueryData`로 순서를 바꾼다. 답이 끊겨도 질문은 서버에 남을 수 있어 실패해도 되돌리지 않는다 |
| 대화 내용 `/api/question-sessions/:id` | `["session", id]` | 이 탭에서 받는 답은 쿼리가 아니라 화면 상태로 두므로 무효화하지 않는다 |
| 퀴즈 홈 `/api/quiz-home` | `["quiz-home", unitId]` | 값이 참이면 다시 받지 않는다. 거짓이면 절 보기 기록이 성공했을 때와 질문의 답을 받는 일이 끝났을 때 무효화한다. 개념 분류는 답을 만들기 전에 저장되므로 답이 끊기거나 실패해도 무효화하되, 서버가 아직 저장하는 중일 수 있어 바로 받지 않고 다음에 열 때 받는다. 처음 받는 요청이 진행 중이면 취소하고 다시 받는다 |
| 지난 문제 `GET /api/quiz-attempts` | `["quiz-attempts"]` | 채점을 보낸 뒤 결과와 상관없이 무효화한다. 응답을 받지 못해도 저장됐을 수 있고, 채점 중에 문제 카드가 사라져도 무효화한다 |

쿼리는 `lib/queries.ts` 한곳에 두고, 무효화도 그 파일의 `refreshQuizHome`, `refreshPastAttempts`로만 한다. 기본값은 다음과 같다.

- `staleTime`과 `gcTime`은 `Infinity`다. 받은 값은 위 표의 때에만 다시 받고, 학습 화면에 머무는 동안 지운다는 판단도 하지 않는다.
- `retry`는 `false`다. 자동 재시도를 켜면 실패 화면이 늦게 떠서 지금의 실패와 다시 시도 동작이 바뀐다.
- 퀴즈 홈은 무효화할 때 닫혀 있어도 바로 다시 받는다. 다시 열 때 지난 기출 문제 안내가 잠깐 보이지 않게 하려는 것이다.
- 대화 목록과 대화 내용은 받은 뒤에 열 대화를 고르거나 받는 중인 답과 합쳐야 해서 `fetchQuery`로 직접 받고, 화면은 쿼리로 상태만 읽는다.

다음은 옮기지 않는다.

- 답변 스트리밍 `lib/answer-stream.ts`: 조각마다 화면에 반영하고, 끊기면 받은 데까지 남기고, 409를 받으면 새 ID로 다시 묻는 흐름이라 쿼리 모델과 맞지 않는다.
- 퀴즈 문제 생성 `POST /api/quiz-problems`: 응답을 반영할지는 `settleQuizSet`의 탭 비교가 정한다. `useMutation`으로 감싸더라도 이 판단은 순수 함수에 남긴다.
- 꺼내 먹기 오늘 세트: 하루에 한 번만 받을 수 있는 요청이라 재시도와 다시 받기를 잘못 설정하면 위험하다. 옮긴다면 `staleTime: Infinity`, `retry: false`로 맨 마지막에 옮긴다.
- 절 보기 기록과 머문 시간 전송: 화면이 결과를 보여 주지 않는 기록 요청이다.

2단계로 Zustand를 들여 다음만 옮긴다.

- `useQuizSet`을 스토어로 옮겨 ref 복사를 없앤다. 스토어는 `advanceQuizSet`, `settleQuizSet`을 부르기만 하고, 규칙은 순수 함수에 남겨 기존 단위 테스트를 그대로 쓴다.
- `createChannel`을 스토어로 바꿔 Provider 없이 본문과 패널이 함께 구독한다.
- 브라우저 저장소 세 벌을 `persist` 미들웨어로 합치는 일은 선택으로 둔다. 학습자별 키와 서버에서 기본값으로 그리는 동작을 지킬 수 있는지 먼저 확인해야 한다.

한 컴포넌트 안에서만 쓰는 메뉴 열림, 안내 문구, 입력 여부 같은 상태는 `useState`로 둔다.

### 실행 지표

흐름은 단원 열기, 퀴즈 탭 3번 열기, 지난 문제 2번 열고 돌아오기, 세 문제 풀기, 결과 화면에서 지난 문제 열기다. 퀴즈 홈은 이 흐름에서 5번 그려진다. 문제를 풀다가 퀴즈 홈으로 가는 길이 결과 화면에만 있어 처음 계획한 "문제 1개 풀기"를 세 문제로 바꿨다. 개발 서버에서 3번 돌렸고, 개발 서버는 Strict Mode로 효과를 두 번 실행해 도입 전 요청 수가 운영의 2배로 나온다.

| 지표 | 도입 전 | 도입 후 | 측정 방법 |
| --- | --- | --- | --- |
| 한 단원에서 퀴즈 홈이 5번 그려질 때 `/api/quiz-home` 요청 수 | 10번, 운영 기준 5번 | 1번 | 측정 스크립트 |

| 지난 문제를 다시 열 때 로딩이 보이는지와 걸린 시간 | 매번 보였다, 0.91~0.92초 | 보이지 않았다, 0.04~0.15초 | 측정 스크립트 |

## 검토한 대안

| 대안 | 장점 | 단점 | 택하지 않은 이유 |
| --- | --- | --- | --- |
| 지금처럼 `useState`와 `useEffect`로 둔다 | 의존성이 늘지 않는다 | 로딩, 재시도, 캐시 코드가 화면마다 반복되고 무효화 경로가 없다 | 데이터를 받는 화면이 늘수록 같은 코드가 늘어난다 |
| 공통 `useFetch` 훅을 직접 만든다 | 번들이 늘지 않는다 | 캐시, 무효화, 중복 요청 제거, 재시도를 직접 만들고 테스트해야 한다 | 결국 TanStack Query의 일부를 다시 만드는 일이다 |
| SWR | TanStack Query보다 가볍다 | mutation 뒤 무효화와 낙관적 업데이트 되돌리기가 TanStack Query보다 단순하지 않다 | 이 프로젝트의 개선 대부분이 무효화에서 나온다. 확인 필요 |
| 서버 컴포넌트와 `router.refresh`로 다시 받는다 | 클라이언트 캐시 코드가 없다 | 학습 패널은 레이아웃에 있고 받는 중인 답과 풀던 문제를 유지해야 해서 새로 그리기에 맞지 않는다 | 패널 상태가 사라질 위험이 있다 |
| 클라이언트 상태도 모두 Zustand로 옮긴다 | 상태가 한곳에 모인다 | 한 컴포넌트에서만 쓰는 상태까지 전역이 되어 오히려 복잡해진다 | 문제가 있는 곳은 ref 복사와 직접 만든 채널뿐이다 |

## 결과

- 서버 데이터를 받는 방식이 하나로 모이고, 로딩과 실패 처리가 같은 모양이 된다.
- 퀴즈 홈과 지난 문제는 바뀌었을 때만 다시 받고, 다시 열 때 스켈레톤 없이 바로 보인다.
- `useQuizSet`의 ref 복사가 사라져 상태와 ref가 어긋날 여지가 없어진다.
- 브라우저 번들이 늘어난다. 정확한 크기는 측정 예정이다.
- 무효화 시점을 빠뜨리면 오래된 값을 보여 줄 수 있다. 지금은 매번 새로 받아 생기지 않는 위험이다. 무효화 시점은 위 표 하나에서 관리한다.
- 쿼리와 스토어 코드는 컴포넌트 테스트 없이 순수 함수와 E2E로 확인한다는 0006 원칙을 따라야 한다. 변환과 판단은 순수 함수로 빼 둔다.

## 다시 검토할 조건

- 측정 결과 요청 수나 스켈레톤 시간 개선이 작고 번들 증가가 크면 1단계를 접고 공통 훅 대안을 다시 본다.
- 학습 패널을 서버 컴포넌트로 다시 그려도 패널 상태를 유지할 수 있게 되면 서버 컴포넌트 대안을 다시 본다.
- 꺼내 먹기 오늘 세트를 여러 번 받을 수 있게 바뀌면 TanStack Query로 옮긴다.
