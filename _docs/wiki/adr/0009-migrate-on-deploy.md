# 0009. DB 마이그레이션은 Vercel 배포 빌드에서 자동으로 적용한다

- 상태: 확정
- 결정 날짜: 2026-11-05
- 결정한 사람: 개발자
- 관련 문서: [0003. Neon Postgres와 Drizzle ORM](0003-neon-postgres-drizzle.md), [0006. 테스트 전략](0006-test-strategy.md), Linear [4-79](https://linear.app/silo0/issue/4-79), PR [#16](https://github.com/silo-4th/silo-4th/pull/16)

## 상황

2026-11-05에 4-61 PR #15를 머지한 뒤 Neon 브랜치의 `drizzle.__drizzle_migrations`를 조회했다. `production`, `preview/develop`, `vercel-dev`는 `0002`까지, `test`는 `0004`까지 적용돼 있었다. `develop` 코드는 `0003_question_sessions`가 만드는 `questions.session_id`에 값을 넣으므로, develop 프리뷰에서 질문 저장이 실패하고 있을 것으로 추정했다. 화면으로는 확인하지 않았다.

결정 시점에 확인한 사실은 다음과 같다.

- 이 프로젝트는 Vercel이 관리하는 Neon 연동을 쓴다. 연동은 git 브랜치마다 운영 DB를 복사해 `preview/<브랜치>` 브랜치를 만들고 배포에 DB 주소를 넣어 줄 뿐, 마이그레이션은 돌리지 않는다. (근거: Neon 문서 [Connecting with the Vercel-Managed Integration](https://neon.com/docs/guides/vercel-managed-integration) "Enable automated preview branching")
- 같은 문서는 빌드 명령에 마이그레이션을 넣어 프리뷰 DB의 스키마를 코드와 맞추라고 안내한다. 다만 연동이 넣는 주소가 빌드 단계에도 있는지는 "배포 시점에 주입"으로만 적혀 있다.
- Drizzle 마이그레이터는 DB에 기록된 마지막 마이그레이션의 `created_at`보다 `_journal.json`의 `when`이 큰 마이그레이션만 실행하고, 대기 중인 마이그레이션을 한 트랜잭션으로 적용한다. (근거: `node_modules/drizzle-orm/pg-core/dialect.js` `migrate`)
- 4-79에서 `0005_quiz_tables`를 푸시한 뒤 두 번 다시 생성했다. 4-61 머지 뒤 번호를 맞출 때와 리뷰를 반영할 때다. `test` 브랜치에는 `0004` 기록이 두 개 남아 있어, 다시 만든 마이그레이션이 한 번 더 적용된 것으로 보인다.

## 결정

1. 저장소 루트 `vercel.json`의 빌드 명령을 `npm run build && npx drizzle-kit migrate`로 둔다. 프리뷰 배포는 `preview/<브랜치>`에, 운영 배포는 `production`에 마이그레이션을 적용하고, 실패하면 빌드가 멈춰 배포되지 않는다. `next build`가 성공한 뒤에만 마이그레이션을 적용해, 배포되지 못한 코드의 스키마가 DB에 남지 않게 한다. 빌드는 DB를 읽지 않으므로 새 스키마 없이도 성공한다. DB를 읽는 페이지는 모두 요청 시점에 학습자를 확인하고 `Suspense` 안에서 그린다.
2. `package.json`의 `build`는 바꾸지 않는다. 로컬 `npm run build`가 `.env.local`의 DB에 마이그레이션을 넣지 않게 하기 위해서다.
3. Vercel 빌드에서는 직접 연결 주소 `DATABASE_URL_UNPOOLED`를 먼저 쓰고, 없으면 `DATABASE_URL`을 쓴다. 로컬에서는 `DATABASE_URL`만 쓴다. Vercel 빌드인지는 `.env.local`을 불러오기 전에 `VERCEL`로 판단한다. `vercel env pull`로 만든 `.env.local`에도 이 키가 들어 있기 때문이다.
4. 운영 `production` 브랜치에는 손으로 마이그레이션을 돌리지 않는다.
5. 푸시한 마이그레이션은 다시 생성하거나 고치지 않고, 바꿀 내용은 새 마이그레이션으로 더한다. 머지 전에 꼭 다시 만들어야 하면 그 PR의 `preview/<브랜치>` 브랜치를 부모 브랜치에서 다시 만든다.
6. 다른 브랜치와 마이그레이션이 충돌하면 `_journal.json`을 손으로 합치지 않는다. 받아 온 쪽 마이그레이션을 그대로 두고 내 마이그레이션을 지운 뒤 `npm run db:generate`로 다시 만든다.
7. 마이그레이션은 이전 코드가 새 스키마에서도 돌아가게 만든다. 마이그레이션이 들어간 뒤 새 배포가 트래픽을 받기 전까지, 그리고 이전 배포로 되돌렸을 때 이전 코드가 새 스키마를 보기 때문이다. 컬럼을 지우거나 필수로 바꾸는 일은 코드를 먼저 배포한 뒤 다음 마이그레이션에서 한다.
8. 배포와 연결되지 않은 `test`, `vercel-dev` 브랜치는 지금처럼 손으로 적용한다.

## 검토한 대안

| 대안 | 장점 | 단점 | 택하지 않은 이유 |
| --- | --- | --- | --- |
| 지금처럼 개발자가 손으로 적용한다 | 설정이 늘지 않는다 | 머지할 때마다 브랜치 여러 개에 따로 적용해야 하고, 이미 운영과 개발 DB가 두 단계 밀렸다 | 실제로 빠뜨렸고, 프리뷰 브랜치는 PR마다 새로 생긴다 |
| GitHub Actions에서 머지 뒤 적용한다 | 빌드와 DB 작업이 나뉜다 | 워크플로와 DB 비밀 값을 새로 관리해야 하고, 프리뷰 브랜치 주소는 Vercel 배포에만 주입된다 | 프리뷰 DB 주소를 Actions에서 얻을 방법이 없다 |
| `package.json`의 `build`에 넣는다 | 설정 파일이 늘지 않는다 | 로컬 `npm run build`가 `.env.local`의 DB에 마이그레이션을 넣는다 | 로컬 빌드는 DB를 바꾸면 안 된다 |
| 빌드 전에 적용한다 | 빌드 중 새 스키마를 읽을 수 있다 | `next build`가 실패해도 DB만 새 스키마로 남고, 이전 코드가 다음 배포가 성공할 때까지 새 스키마를 본다 | 빌드가 DB를 읽지 않아 얻는 것이 없다. PR #16 CodeRabbit 리뷰에서 지적됐다 |

| 앱이 시작할 때 적용한다 | 빌드와 무관하게 적용된다 | 서버리스 함수가 뜰 때마다 동시에 실행되고, 실패해도 배포가 멈추지 않는다 | 실패한 마이그레이션이 배포를 막지 못한다 |

## 결과

- `develop`에 머지하면 `preview/develop`에, `main`에 머지하면 `production`에 마이그레이션이 들어간다. 다음 배포 때 밀려 있던 `0003`부터 한 번에 적용된다.
- 마이그레이션이 실패하면 트랜잭션이 되돌아가고 배포가 멈춘다. 빌드 로그에서 원인을 본다.
- `next build`가 실패하면 마이그레이션을 돌리지 않아 DB가 바뀌지 않는다.
- 마이그레이션이 성공한 뒤 배포 파일 업로드가 실패하면 DB만 새 스키마가 된다. 다시 배포해서 푼다.
- 4-77의 `0003`은 `questions.session_id`를 필수로 만들어 결정 7에 맞지 않는다. `main` 코드는 이 값 없이 질문을 저장하므로, 운영에 `0003`이 들어간 뒤 새 배포가 트래픽을 받기 전까지 질문 저장이 실패한다. 운영 질문이 1건뿐이라 받아들인다.
- Vercel에서 `0003` 이전 배포로 되돌리면 빌드 없이 이전 코드가 뜨므로 질문 저장이 실패한다. 되돌리기 대신 고친 코드를 새로 배포한다.
- `main` 배포 전에는 운영 백업 브랜치를 만들어 둔다. 11/2의 `backup-before-login-tables-2026-11-02`와 같은 방식이다.
- 같은 git 브랜치를 동시에 두 번 배포하면 두 빌드가 같은 DB에 마이그레이션을 시도할 수 있다. 한쪽은 트랜잭션 충돌로 실패하고, 다시 배포하면 된다.

## 다시 검토할 조건

- 프리뷰 빌드에서 DB 주소가 들어오지 않아 마이그레이션이 실패하면 빌드 단계 주입 방식부터 다시 본다.
- 오래 걸리거나 데이터를 크게 바꾸는 마이그레이션이 생기면 배포와 분리해 적용하는 방식을 검토한다.
