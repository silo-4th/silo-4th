## 상황

기능 구현을 본격적으로 시작하기 전에 테스트 도구를 도입해야 했다. 0001에서 테스트 도구는 의존성과 배포 방식이 정해질 때까지 미뤄 두었다. (근거: [개발 규칙](../dev-rules.md) "아직 도입하지 않은 규칙")

AI가 코드와 테스트를 함께 쓰면 구현에 맞춰 테스트를 끼워 맞추고, 요청하지 않은 테스트를 계속 늘린다. 개발자가 가져온 계획서는 이 문제를 막으려고 케이스는 사람이 정하고 AI는 확정된 케이스만 코드로 옮기는 원칙을 세웠다. (근거: `raw/2026-11-02-test-adoption-plan.md` "1. 도입 배경과 목적", "2. 핵심 원칙")

이 서비스의 핵심 요구는 학습자, 질문, AI의 답, 확인, 이해 상태, 사용의 기록 여섯 가지를 빠짐없이 남기는 것이다. 계획서의 선정 기준인 돈, 데이터, 권한 가운데 이 프로젝트에 해당하는 위험은 데이터와 권한이다. (근거: [기술 스택](../tech-stack.md) "근거", `raw/2026-11-02-test-adoption-plan.md` "4. 핵심 로직과 주요 흐름 선정 방법")

결정 시점에 확인한 사실은 다음과 같다.

- Next.js 16.4.3 공식 문서는 Vitest가 `async` 서버 컴포넌트를 지원하지 않으므로 이런 컴포넌트는 E2E로 테스트하라고 안내한다. (근거: `node_modules/next/dist/docs/01-app/02-guides/testing/index.md` "Async Server Components", `testing/vitest.md`)
- DB 접근은 대화형 트랜잭션이 없는 `drizzle-orm/neon-http`로 한다. (근거: [0003](0003-neon-postgres-drizzle.md) "결과")
- 로그인은 Better Auth로 붙인 Google OAuth라, 자동화된 브라우저로 로그인 화면을 통과하기 어렵다. (근거: [0004](0004-social-login.md) "결정")
- `lib/db/schema.ts`는 아직 비어 있고, 테이블은 기록 구조 회의에서 정한 뒤 추가한다.

## 결정

계획서의 핵심 원칙 다섯 가지를 따른다. 테스트 케이스는 노션 DB에서 사람이 확정하고, AI는 노션 DB에서 상태가 확정인 케이스만 읽어 테스트 코드로 옮긴다. Linear 문서를 raw에 저장하지 않고 Linear에서 바로 조회하는 것처럼, 테스트 케이스도 저장소에 파일로 두지 않고 노션 DB에서 바로 조회한다.

테스트는 세 유형으로 나눈다.

| 유형 | 도구 | 대상 |
| --- | --- | --- |
| 단위 | Vitest | 함수 하나의 입력과 출력, 경계값, 예외. 학습일 계산 같은 공통 변환 로직 |
| 통합 | Vitest와 실제 테스트 DB | DB를 변경하는 서버 코드와, 학습자별로 조회 범위를 제한하는 서버 코드. Route Handler나 Server Action을 직접 호출하고 DB에 남은 결과나 돌려준 범위를 확인한다. Anthropic SDK는 목으로 바꾼다 |
| E2E | Playwright | 주요 사용자 흐름 3~5개. 대표 입력 한두 개로 흐름이 끝까지 이어지는지 확인한다. `async` 서버 컴포넌트도 여기서 확인한다 |

React Testing Library로 하는 컴포넌트 테스트는 두지 않는다. 화면은 E2E가 확인하고, 화면 안의 변환 로직은 함수로 빼서 단위 테스트한다.

통합 테스트를 DB를 변경하거나 학습자별로 조회를 제한하는 곳에 두는 이유는 다음과 같다.

- 기록이 빠짐없이 저장되는지, 학습자 A가 B의 기록을 읽거나 고칠 수 없는지는 서버 코드와 DB가 맞물리는 곳에서 틀린다. 단위 테스트에서 DB를 목으로 바꾸면 목이 실제 DB와 다르게 동작해도 테스트가 통과한다.
- E2E는 화면에 보이지 않는 기록을 확인하기 어렵다. AI 호출 실패, 중복 요청, 학습자 간 접근 같은 경우를 하나씩 브라우저 흐름으로 만들면 느리고 깨지기 쉽다.
- Google OAuth를 E2E에서 통과하려면 인증 우회 장치가 필요하다. 권한 검증까지 E2E에 맡기면 그 장치에 기대는 범위가 커진다. 통합 테스트에서는 세션을 직접 만들어 넣는다.
- `neon-http`는 대화형 트랜잭션이 없어, 여러 기록을 한꺼번에 저장하다 실패하면 일부만 남을 수 있다. 이 문제는 실제 DB를 대상으로 해야 드러난다.

## 검토한 대안

| 대안 | 장점 | 단점 | 택하지 않은 이유 |
| --- | --- | --- | --- |
| 단위 테스트와 E2E만 둔다 | 도구와 테스트 DB 설정이 줄어든다 | 실제 DB 저장과 학습자별 접근 제한을 E2E로만 확인해야 한다 | 이 서비스의 가장 큰 위험인 기록 누락과 권한 문제를 확인할 곳이 마땅치 않다 |
| 계획서대로 통합 테스트에 React Testing Library 컴포넌트 테스트를 포함한다 | 화면 단위의 동작을 빠르게 확인한다 | 계획서 안에서도 통합 테스트 정의가 API와 DB 연동, 컴포넌트 검증으로 엇갈린다. `async` 서버 컴포넌트는 Vitest로 테스트할 수 없다 | 화면은 E2E가 맡고 로직은 함수로 빼면 컴포넌트 테스트가 확인할 몫이 적다 |
| 통합 테스트에서도 DB를 목으로 바꾼다 | 테스트 DB 없이 빠르게 돈다 | 목과 실제 DB가 다르게 동작해도 통과한다 | 확인하려는 대상이 실제 저장 결과라 목으로는 목적을 이루지 못한다 |
| 케이스 원본을 Linear 이슈로 관리한다 | `_docs/CLAUDE.md`의 Linear 우선 원칙과 맞는다 | 사용자 정의 필드가 없어 상황, 행동, 기대 결과를 본문 텍스트로만 둔다. 워크플로 상태가 개발 이슈와 섞여 전용 팀을 따로 만들어야 한다 | 칸별 필터와 표 보기가 필요해 노션 DB를 택했다 |
| 케이스 원본을 Linear 문서 하나에 표로 둔다 | 버전 기록이 남고 Linear 안에서 끝난다 | 행마다 상태와 담당자를 줄 수 없고 거르거나 묶어 볼 수 없다 | 위와 같다 |
| 확정 케이스를 저장소의 마크다운으로 내보낸다 | AI가 노션에 접근하지 않아도 케이스를 읽고, 변경 이력이 git에 남는다 | 같은 케이스를 노션과 저장소 두 곳에서 관리해야 하고, 노션을 고칠 때마다 다시 내보내고 커밋해야 한다 | 관리 지점만 늘고 번거롭다. 노션도 페이지 기록을 남긴다 |
| 단위 테스트 도구로 Jest를 쓴다 | 자료가 많고 Next.js 공식 문서도 안내한다 | 계획서는 Vitest가 TypeScript와 ESM을 바로 지원해 AI가 반복 실행하기에 낫다고 봤다 | 아직 테스트 설정이 없어 Jest를 유지할 이유가 없다. 두 도구는 문법이 거의 같아 나중에 옮기기도 어렵지 않다 |

## 결과

- AI가 쓸 수 있는 테스트가 확정된 케이스로 한정되어, 테스트가 구현에 끌려가거나 의미 없이 늘어나는 일을 줄인다.
- 기록 저장과 학습자별 접근 제한을 실제 DB로 확인하므로, AI가 쿼리 조건을 빠뜨려도 화면이 멀쩡해 보이는 문제를 잡는다.
- 테스트 DB가 필요하다. Neon 브랜치 하나를 테스트 전용으로 둔다. 통합 테스트는 DB를 오가므로 단위 테스트보다 느리고, 실행 명령을 나눠야 한다.
- 2026-11-02 4-48에서 운영 브랜치를 부모로 Neon `test` 브랜치를 만들었다. 마이그레이션은 이 브랜치에 먼저 적용한다. 주소와 키는 저장소에 올리지 않는 `.env.test.local`에 두고, `vitest.config.ts`가 통합 테스트 프로젝트에만 이 파일을 읽어 넣는다. 원격 DB를 여러 번 오가므로 통합 테스트의 제한 시간을 30초로 늘렸다. 파일에 넣을 키는 저장소 루트 `README.md`의 "통합 테스트" 항목에 있다.
- 케이스 원본이 노션에 있어 `_docs/CLAUDE.md`의 "원본이 다르면 Linear를 우선한다"는 원칙의 예외가 생긴다. 테스트 케이스에 한해서는 노션 DB가 원본이고, 저장소에는 사본을 두지 않는다.
- AI가 테스트를 쓰려면 노션에 접근할 수 있어야 한다. 노션 MCP나 `ntn` CLI로 Test-case DB를 조회한다.
- 2026-11-02에 `vitest` `5.0.5`와 `@playwright/test` `1.64.1`을 설치했다. 단위와 통합은 `vitest.config.ts`의 `projects`로 나누고, 파일 이름을 각각 `*.test.ts`, `*.integration.test.ts`로 짓는다. 실행 명령은 `npm test`, `npm run test:integration`, `npm run test:e2e`다. tsconfig 경로는 Vite 8의 `resolve.tsconfigPaths`로 풀어 Next.js 문서가 안내하는 `vite-tsconfig-paths`를 쓰지 않았다. `lib/db`가 import하는 `server-only`는 Next.js 밖에서 오류를 던지므로 Vitest에서는 빈 모듈로 바꾼다. 화면을 그리지 않으므로 `jsdom`과 `@vitejs/plugin-react`도 설치하지 않았다. E2E는 서비스가 PC 전용이라 Desktop Chrome 하나로만 돌린다.
- 노션 DB의 속성은 케이스 ID, 이름, 핵심 기능, 테스트 유형, 상태, 우선순위, Linear 이슈, 위험 분류, 확정일이다. 계획서의 속성 표에서 바꾼 점은 다음과 같다. (근거: `raw/2026-11-02-test-adoption-plan.md` "노션 데이터베이스 구조")
  - 상황, 행동, 기대 결과는 속성에 두지 않고, 각 케이스 페이지 본문의 `## Given`, `## When`, `## Then` 제목 아래에 적는다. E2E 절차는 `## Steps` 아래에 적는다. AI는 이 제목을 기준으로 본문을 읽는다.
  - 케이스는 모두 개발자가 맡으므로 담당자 속성을 두지 않는다.
  - PRD가 Linear 문서라 PRD 기능 번호 대신 핵심 기능 키워드를 다중 선택으로 둔다.
  - 케이스 ID는 노션 ID 속성에 접두사 `TC`를 붙여 `TC-1`처럼 자동으로 매긴다.
  - Linear 이슈는 `[4-48](url)`처럼 이슈 번호에 링크를 건 텍스트로 넣는다.
- 2026-11-03 4-58에서 개발자가 E2E 로그인 방식을 정했다. Google 로그인 화면은 자동화로 통과할 수 없으므로, 테스트 코드가 Better Auth가 로그인 끝에 남기는 결과를 직접 만든다.
  - `e2e/fixtures.ts`가 테스트 DB에 저장 동의를 마친 테스트 학습자와 세션 행을 만들고, `AUTH_SECRET`으로 서명한 세션 쿠키를 브라우저에 넣는다. 테스트가 끝나면 실패해도 학습자를 지운다.
  - 처음 제안했던 "테스트 환경에서만 켜지는 세션 주입" 대신 이 방식을 택했다. 앱 코드에 테스트용 우회 장치가 없어 운영에서 잘못 켜질 위험이 없기 때문이다.
  - 쿠키 형식은 Better Auth 내부 구현을 따른다. Better Auth를 올렸을 때 E2E 로그인이 깨지면 쿠키 이름과 서명 방식을 먼저 확인한다.
- E2E도 테스트 학습자를 만들고 지우므로 Neon `test` 브랜치에 붙는다. `playwright.config.ts`가 `.env.test.local`을 읽어 3100번 포트에 개발 서버를 따로 띄우고, 이미 떠 있는 서버는 운영 DB에 붙어 있을 수 있어 다시 쓰지 않는다. 파일이 없으면 실행 전에 실패한다. Next.js 16은 한 프로젝트에 개발 서버를 하나만 띄우므로, E2E 전에 `npm run dev`를 끈다.

다음은 Claude가 제안했고 개발자가 아직 정하지 않았다. 모두 `제안`이다. 정하면 이 ADR과 [개발 규칙](../dev-rules.md)을 고친다.

- 0001의 원칙대로 "확정된 테스트는 AI가 고치지 않는다"를 md가 아닌 PreToolUse 훅으로 강제한다. 이미 있는 `*.test.ts`, `*.spec.ts` 수정을 막고, 새 파일 생성은 허용한다.
- 테스트 이름에 케이스 ID를 넣고, 그 ID가 노션 DB의 확정 케이스에 있는지 검사하는 스크립트를 `npm run check`에 붙인다.
- Stop 훅에는 단위 테스트만 넣고, 통합 테스트와 E2E는 따로 실행하거나 CI에서 돌린다.

## 다시 검토할 조건

- 통합 테스트가 느려 작업 흐름을 눈에 띄게 늦추면 실행 시점과 범위를 다시 정한다.
- `neon-http`를 Pool 방식으로 바꾸면 트랜잭션 관련 케이스를 다시 본다.
- AI가 노션에 접근할 수 없는 환경에서 테스트를 써야 하면 저장소 사본을 다시 검토한다.
- 화면 로직이 커져 E2E만으로 원인을 찾기 어려워지면 컴포넌트 테스트를 다시 검토한다.
