# 0011. 기본 문제는 TS 모듈에서 만든 마이그레이션으로 넣고, 바꿀 때마다 새 마이그레이션으로 교체한다

- 상태: 확정
- 결정 날짜: 2026-11-08
- 결정한 사람: 개발자
- 관련 문서: [0009. DB 마이그레이션은 Vercel 배포 빌드에서 자동으로 적용한다](0009-migrate-on-deploy.md), [0006. 테스트 전략](0006-test-strategy.md), Linear [4-90](https://linear.app/silo0/issue/4-90)

## 상황

본 절도 대화도 없이 퀴즈 탭을 열면 AI를 부르지 않고 그 단원의 기본 문제를 보여 준다. 기본 문제가 DB에 없으면 퀴즈 생성 API가 500을 돌려준다. Linear 4-90 본문에 근거가 있다.

기본 문제는 4-14의 정답 검수 결과에 따라 운영 전까지 여러 번 바뀔 수 있다. 결정 시점에 확인한 사실은 다음과 같다.

- Drizzle 마이그레이터는 DB에 기록된 마지막 마이그레이션보다 `when`이 큰 파일만 실행한다. 이미 적용된 파일을 고쳐도 그 DB에서는 다시 돌지 않는다. 근거는 ADR 0009 "상황"이다.
- ADR 0009 결정 5는 푸시한 마이그레이션을 다시 만들거나 고치지 않는다고 정한다. PR을 올리면 `preview/<브랜치>`, develop에 머지하면 `preview/develop`에 마이그레이션이 들어가고, `test` 브랜치에는 손으로 적용한다.
- `quiz_attempts.problem_id`는 `quiz_problems.id`를 `ON DELETE no action`으로 참조한다. 누가 푼 문제는 지울 수 없다.
- `0004`, `0005`를 다시 만들었을 때 `test` 브랜치에 같은 마이그레이션이 한 번 더 적용됐다. 근거는 ADR 0009 "상황"이다.

티켓의 처음 계획은 운영 전에는 마이그레이션 한 파일을 다시 만들고, 운영 뒤에는 손으로 교체 마이그레이션을 쓰는 것이었다. 이 계획대로 하면 PR을 푸시한 뒤에는 `preview/develop`과 `test`에 옛 문제가 남는다.

## 결정

1. 기본 문제의 원본은 `lib/default-quiz-problems.ts`의 `DEFAULT_QUIZ_PROBLEMS` 하나다. 처음에는 `npm run quiz:defaults:generate`가 퀴즈 생성 API와 같은 `generateQuizProblem`으로 만들어 이 파일을 쓴다. 단원마다 5개 이상, 절마다 하나 이상이 되게 절을 돌아가며 고르고, 모두 객관식으로 만든다. 모양 검사를 통과하지 못하거나 "본문", "위 표"처럼 학습 화면을 가리키는 문제는 버리고 다시 만든다. 지문 안에 직접 만들어 넣은 작은 데이터 표는 문제만 보고 풀 수 있으므로 받는다. 이 해석은 2026-11-08에 개발자가 정했다.
2. 기본 문제를 바꿀 때는 운영 전후 모두 모듈을 고치고 `npm run quiz:defaults:migration`으로 새 마이그레이션을 만든다. 마이그레이션 태그는 `_default_quiz_problems`로 끝난다. 푸시한 기본 문제 마이그레이션은 고치지 않는다.
3. 마이그레이션 SQL은 `lib/default-quiz-problems-sql.ts`의 `defaultQuizProblemsSql`이 만들고, 어느 DB에 몇 번 적용해도 활성 기본 문제가 모듈과 같아지게 한다.
   - 문제 ID는 절 ID와 문제 내용의 SHA-256 해시로 만든다. 내용이 같으면 늘 같은 ID이고, 한 글자라도 바뀌면 새 ID다.
   - 모듈의 문제는 `ON CONFLICT ("id")`로 넣고, 이미 있으면 `retired_at`만 비운다.
   - 모듈에 없는 활성 기본 문제는 `retired_at`을 채워 내린다. 지우지 않으므로 풀이는 그때 본 문제를 계속 가리킨다.
   - 학습자에게 만든 문제는 건드리지 않는다.
4. 기본 문제를 고르는 규칙을 보는 통합 테스트 TC-116, TC-136, TC-138은 단원에 테스트가 넣은 문제만 있다고 가정하지 않고, 마이그레이션이 넣은 기본 문제를 DB에서 읽어 단언한다. TC-116은 내려간 문제를 빼는지 보려고 내려간 문제 하나만 넣는다. 응답에 새면 안 되는 문제를 넣는 TC-122, TC-126, TC-127은 케이스대로 테스트 문제를 넣는다.
5. 생성 스크립트는 만든 객관식 문제의 정답 자리를 문제마다 돌려 둔다. AI가 정답을 앞쪽 보기에 두는 경향이 있어서, 처음 만든 28문제는 첫 번째 보기가 정답인 문제가 13개였고 네 번째 보기가 정답인 문제는 없었다.

## 검토한 대안

| 대안 | 장점 | 단점 | 택하지 않은 이유 |
| --- | --- | --- | --- |
| 운영 전에는 한 파일을 다시 만든다 | 마이그레이션 파일이 하나로 끝난다 | 이미 적용된 DB에서는 다시 돌지 않고, `when`이 바뀌면 같은 문제가 두 벌 들어간다 | 푸시 뒤 `preview/develop`과 `test`가 옛 문제로 남고 ADR 0009 결정 5에 어긋난다 |
| 배포 빌드에서 마이그레이션 뒤 동기화 스크립트를 돌린다 | 바꿀 때마다 파일이 늘지 않는다 | DB를 바꾸는 길이 마이그레이션 밖에 하나 더 생기고, `test`와 `vercel-dev`에는 따로 돌려야 한다 | ADR 0009의 빌드 명령을 바꿔야 하고, 얻는 것에 비해 관리할 것이 늘어난다 |
| 테스트 동안 시드를 숨겼다가 되돌린다 | 기존 테스트 단언을 그대로 둔다 | 같이 쓰는 `test` 브랜치의 데이터를 테스트가 바꾸고, 도중에 멈추면 시드가 숨겨진 채 남는다 | 다른 브랜치의 테스트까지 깨질 수 있다 |
| 테스트 전용 단원과 절을 만든다 | 시드와 완전히 떨어진다 | 단원, 절, 질문을 만들고 지우는 준비 코드가 늘어난다 | 고르는 규칙은 시드 위에서도 확인되고, 시드가 없을 때의 실패는 TC-146이 함께 알려 준다 |

## 결과

- 기본 문제를 몇 번 바꿔도 운영, 프리뷰, `test` 브랜치가 같은 활성 기본 문제를 갖는다. 노션 TC-149가 이를 확인한다.
- 모듈만 고치고 마이그레이션을 만들지 않으면 노션 TC-147이 실패한다.
- 바꿀 때마다 마이그레이션 파일이 하나씩 늘어난다. 대신 바뀐 문제와 내려간 문제가 PR에서 SQL diff로 보인다.
- 문제를 한 글자만 고쳐도 새 문제가 되므로, 고치기 전 문제의 풀이 기록은 고치기 전 문제를 가리킨다.
- 4-90을 머지하기 전 코드의 TC-116, TC-136, TC-138은 단원의 기본 문제가 테스트가 넣은 것뿐이라고 가정한다. `test` 브랜치에 기본 문제를 넣은 뒤에는 그런 브랜치를 develop에 rebase해야 이 테스트가 통과한다.

## 다시 검토할 조건

- 기본 문제 마이그레이션이 너무 많아져 리뷰하기 어려워지면 배포 빌드의 동기화 스크립트를 다시 검토한다.
- 기본 문제를 학습자별로 다르게 내야 하면 이 방식을 다시 본다.
